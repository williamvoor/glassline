You are going to spec and then build a small app. An earlier session explored the
technology and verified the facts below. Treat them as findings, not as code to keep:

## 1. What the app does

A user asks a question in plain English about a Postgres database (or asks the agent to
"find something interesting"). An LLM agent explores the schema, writes and runs SQL, and
answers with a generated UI: text, metrics, tables and charts, rendered in a web client.

- The database's domain and schema description are known in advance and given to the agent.
- SQL is generated by the LLM.
- The UI is generated by the LLM as A2UI (https://a2ui.org), using the **A2UI Express**
  inference format.
- The first dataset is AusTender (Australian government contracts). The design must not
  hard-code AusTender: the domain description and the allowed schemas are configuration.

## 4. Verified findings from the exploration

### LiteLLM and the Meta Model API
- LiteLLM reads `META_API_KEY`; the route prefix is `meta/`; the default base is
  `https://api.meta.ai/v1` (override with `META_API_BASE`). Meta's own docs call the key
  `MODEL_API_KEY`, which LiteLLM ignores.
- `GET https://api.meta.ai/v1/models` with the key lists: `muse-wonder-1.0`,
  `muse-spark-1.3`, `muse-spark-1.3-contributor`, `muse-spark-1.2`,
  `muse-spark-1.2-contributor`, `muse-spark-1.1`, `muse-image-1.0`,
  `muse-voice-transcribe-1.0`, `sam-3.1`.
- Do not use `-contributor` models by default: per third-party docs, Meta may train on
  prompts and completions sent to them.
- Tool calling works on both models through `litellm.completion(..., tools=[...])`. Asked
  "How many rows are in core.contract?", both called `run_sql` with a correct
  `SELECT COUNT(*) FROM core.contract`. Spark 1.3: 4.2 s; Wonder 1.0: 2.5 s; about 500 input
  tokens each.
- **LiteLLM bug:** with `litellm==1.106.6`, any call that passes `tools=` fails with
  `ModuleNotFoundError: No module named 'mcp'`, because it imports
  `litellm/proxy/_experimental/mcp_server/catalog.py`. Adding the `mcp` package as a
  dependency fixes it. Pin LiteLLM to an exact version and commit `uv.lock` (LiteLLM has
  had compromised PyPI releases in the past).

### Prompt caching (Meta Model API)
- Caching is automatic: no flag, no breakpoints. A request whose prompt starts with the same
  tokens as a recent one reuses that prefix. Matching runs from the first token and stops at
  the first difference. Docs: https://dev.meta.ai/docs/prompt-caching
- Cached input on Muse Spark costs $0.15 per million tokens instead of $1.25 (no extra
  charge for writing to the cache). Pricing: https://dev.meta.ai/docs/pricing-rate-limits
- No minimum prefix length or TTL is documented. Prefixes are evicted under load or after
  inactivity. The Responses endpoint accepts `prompt_cache_retention: "24h"` as a hint.
- LiteLLM passes the count through in `usage.prompt_tokens_details.cached_tokens`.
- Measured on Muse Spark through LiteLLM, with the A2UI prompt (about 4.9k tokens) as the
  prefix: without a cache key, hits were unreliable (in five calls after a first one, only
  one hit). With `prompt_cache_key` set, every call after the first hit (4,849 cached
  tokens). The sample is small.

### A2UI SDK, Express and macros
- Express is the SDK's compact, Python-like UI language: one component per line, variable
  name = component ID, positional args in catalog-schema order, `_` skips an argument,
  `$/path` binds to the data model, `Event("name", {...})` declares an action. The SDK
  compiles it into standard A2UI JSON messages. Spec:
  https://a2ui.org/specification/proposals/express/a2ui_express/
- Express does **not** stream: it is compiled once the full reply has arrived (Direct JSON
  can stream). Google recommends running the model with thinking/reasoning off for Express.
  Google's published benchmarks are on Gemini only; Express quality on Muse models is
  unmeasured.
- The generated prompt tells the model to wrap Express in `<a2ui>` … `</a2ui>` tags. A code
  fence is not recognised.
- **Macros are the key design tool.** A `@macro` function (from
  `a2ui.transformers.macros`) becomes a component the model can call, and is expanded
  server-side into primitive components before anything reaches the client. Use macros so
  the model never retypes data: it runs SQL, gets a result ID, and writes
  `chart=BarChart("q1", "supplier", "total", "Top suppliers")`; the macro reads the stored
  rows and builds the chart. Every number on screen must come from the database.
- The macro docs are in the A2UI repo at
  `python/a2ui_agent/src/a2ui/transformers/macros/README.md`. A working reference is
  `samples/community/macros/` (see `macro_runtime.py` for the wiring, and
  `macros/employee_salary_card.py` for a macro that looks data up server-side).
- There is no Python builder for VegaChart. A minimal one works:

  ```python
  from typing import Any, Literal
  from a2ui.builder.core.base_node import ComponentBuilderNode

  class VegaChart(ComponentBuilderNode):
      component: Literal["VegaChart"] = "VegaChart"
      spec: dict[str, Any]
      height: int | None = None
  ```

- This wiring was verified end to end on a hand-written Express reply (not yet on model
  output). `parse_response` validated it, and expansion produced a `Column` with a `Text`
  title and a `VegaChart` whose `spec.data.values` held the stored rows:

  ```python
  expander = MacroExpander([BarChart])
  catalog = expander.transform_to_inference_catalog(BasicCatalog("0.9.1"))
  fmt = ExpressFormat(catalogs=[catalog], surface_id="main", version="v0.9.1")
  system_snippet = fmt.prompt_generator.generate()
  parts = fmt.create_parser().parse_response(model_reply)   # TextPart / A2uiPart
  msgs = [m for p in parts if isinstance(p, A2uiPart) for m in p.a2ui]
  typed = [TypeAdapter(AgentToRendererMessage).validate_python(m) for m in msgs]
  transport = expander.transform_to_transport(typed)        # what the client receives
  ```

- The generated system snippet is about 20k characters (about 5k tokens) with the basic
  catalog plus one macro. `MacroExpander(..., passthrough_components=[...])` can drop basic
  components the model does not need.
- The basic catalog (v0.9) has: AudioPlayer, Button, Card, CheckBox, ChoicePicker, Column,
  DateTimeInput, Divider, Icon, Image, List, Modal, Row, Slider, Tabs, Text, TextField,
  Video. **No table and no chart.** Tables must be a macro (e.g. a `List`/`Row`/`Text`
  grid); charts use VegaChart.

### Client side
- VegaChart is a Lit web component in the A2UI repo at `typescript/catalogs/vegachart`
  (package `@a2ui/catalog-vegachart` 0.1.0, **not published on npm**). Vendor it into
  `client/` (Apache-2.0: keep the licence header), or depend on it another way that does
  not need the A2UI clone at runtime. Usage: register it alongside the basic catalog,
  `new MessageProcessor([basicCatalog, vegachartCatalog])`. The standalone sample is
  `samples/vegachart/` in the repo.
- The working sample clients use `@a2a-js/sdk` `^0.3.13`. npm's latest is 1.3.0. Match the
  client's A2A version to the Python server's `a2a-sdk` (0.3.x) and check they interoperate.
- The Lit sample shell is `samples/client/lit/shell` in the repo. It was run successfully
  against the repo's Node restaurant agent in Express mode.

## 5. Open risks: resolve these first, in a spike, before the full spec

1. **Mixed-catalog surface.** The SDK emits `createSurface` with the *basic* catalog ID,
   but after macro expansion the surface contains `VegaChart`. The repo's VegaChart sample
   does the opposite (VegaChart catalog ID, with Card/Column/Text inside). Find out what
   the Lit client renders in each case, and what the agent-side validator accepts, and
   pick an approach (for example a merged catalog with its own ID, or putting VegaChart in
   the base catalog given to `MacroExpander`).
2. **Muse Spark writing Express.** Run a few real prompts through `meta/muse-spark-1.3`
   with the generated snippet and measure: valid-Express rate on the first try, retries needed,
   latency, tokens. Compare with Direct JSON.
3. **Schema context size.** The full data dictionary will not fit in every prompt. Decide
   between a curated summary of the relevant tables plus a `describe_table` tool, retrieval
   from the dictionary, or both.
4. **Slow queries on large tables.** Steer the model toward the views and indexed columns,
   and enforce limits (section 6).

## 6. Hard requirements

**SQL safety** (the LLM writes the SQL):
- Connect only with the read-only login. Never use the `fti` superuser.
- Run every query in a `READ ONLY` transaction with a `statement_timeout` (start at about
  15 s) and a row cap on what is fetched and stored (for example 5,000 rows), and say in the
  result when it was truncated.
- Restrict which schemas the agent may query, from configuration.
- Treat text that comes back from the database as untrusted. It goes to the model as data,
  never as instructions.
- Return SQL errors to the model as tool results, so it can correct itself, with a cap on
  the number of tool-loop iterations.

**Data integrity:** numbers, labels and rows shown in charts, tables and metrics come from
stored query results through macros, never retyped by the model. Show the SQL behind each
visual (for example a collapsible "SQL" text under it), so a user can check it.

**Prompt caching:**
- Order every prompt from most stable to least stable: the A2UI format rules and catalog
  first, then the schema and domain description, then the conversation and tool results.
- Never put per-request values (today's date, session IDs, query IDs, timestamps) in the
  system prompt or anywhere before the stable parts; they break the cache on every request.
- Keep the generated prefix byte-for-byte identical between requests (no reordered dict
  keys, set iteration or other nondeterminism in the prompt text). Add a test for this.
- Send a fixed `prompt_cache_key` (for example one per dataset, from configuration).
- Log prompt tokens and cached tokens for every model call, so the hit rate is visible.

**Configuration:** model, format (express / direct_json), database URL, allowed schemas,
domain-description files, timeouts and caps all come from env or a config file.

**Process and code:**
- Write tests alongside the code, not afterwards. When fixing a bug, first add a
  regression test that fails for the reason the bug describes.
- Tests must not call a real model or need the network. Use a stub model that returns
  canned tool calls and canned Express. Database tests may use the real read-only DB or a
  Testcontainers Postgres; say which.
- Avoid premature abstraction: wait until a pattern appears three times.
- Never put secrets in code, logs, test fixtures or commits.
- Do not commit unless asked. If the project becomes a git repo, look for a `.gitmessage`
  template and follow it.
