# 10. A BarChart on a large Board Result draws every row and is unreadable

**Status:** open · **Opened:** 2026-11-04 · **Source:** manual check 4 of SPEC §18 slice 4 Part B (B-M)

## Problem

`BarChart` has no cap on the number of bars. In ordinary answers the model writes its own SQL
with a `LIMIT`, so this rarely shows. A typed question asked while a Board is off its defaults
gets the Board pair, and the model may chart a Board Result directly. Board Results aren't
limited for charting: the Explorer's `share` query returns one row per agency.

## Evidence

- Explorer Board, Control set to `limited`, typed question "Which agencies spent the most?".
  Agent log 2026-11-04 17:22:51–17:22:56: `board pair: board=b1 results=4`, then one model call
  (`prompt=10804 cached=9713`) with no `run_sql`.
- The answer's "Top agencies – limited procurement" `BarChart` is on the Board's `share` Result
  (162 rows). All 162 horizontal bars are drawn, and the agency labels overlap into a solid block.
- Screenshot: the session scratchpad's `check4-limited.png` (not kept in the repo).
- `macros.py` caps the Treemap (`MAX_TREEMAP_TILES = 12`) and `Timeline` ("Showing 30 of N
  bars"), but not `BarChart`.

## Options

1. **Cap `BarChart`** at N bars in displayed order, with a "Showing N of M bars" caption, like
   `Timeline`; or fold the rest into an "Other" bar, like the Treemap. This protects ordinary
   answers too, and needs no model change.
2. **Tell the model, in the Board pair's purpose text,** to re-query with a `LIMIT` rather than
   chart a large Board Result. This costs prompt tokens and is only as reliable as the model.
3. Both.

## Decision needed

- Which option, and N. `Timeline` uses 30, and the Treemap 12.
- With option 1, "Other" or a plain cut: an "Other" bar is clickable in neither the Treemap nor
  here, and it can dwarf the real bars, as it does in the Treemap.
- Whether `LineChart` needs the same cap. It reads by x position, so many points are fine but
  many series are not.
