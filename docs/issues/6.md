# 6. An Ask about an evicted Drill-down names a Result the model has never received

**Status:** open · **Opened:** 2026-11-03 · **Source:** code review and re-review, reproduced with a capped ResultStore

**Priority:** P2

**Problem.** `ExplorerExecutor._ask` in
`explorer/agent/src/explorer_agent/executor.py` calls `restore_result` for the clicked
source. If the source Result was evicted, it is restored under a fresh Result ID. Only
`resolved.kind == "row"` queues a synthetic tool result, however. The Ask button on a
Drill-down has kind `drill_down`, so its user text names the fresh ID without providing that
ID's columns or rows to the model. A previous synthetic result, if still in history, names
the old ID instead.

**Evidence.** With `ResultStore(max_results=1)`, register a Drill-down source for `r1`, then
add another Result to evict it. Resolve the Drill-down's Ask button and call `_ask` with a
stub answerer. The answerer receives
`Ask: explain the Drill-down in Turn 1, Level 2 (Result r3).`, but
`conv.actions.take_pairs()` returns `[]`. The source still holds the rows and `r3` exists
in the store; the missing step is supplying it to the model. The default store reaches the
same condition after enough Results are created while the source remains registered.

**Options.**

- Queue a fresh Drill-down result pair for an explanation Ask, using the restored ID and
  a unique call ID for the new model run.
- Reuse an existing pending pair only if it supplies the current Result ID; otherwise
  refresh it before calling the model.

**Acceptance criteria.**

- Add a regression test that evicts a Drill-down Result while retaining its action source,
  then clicks its Ask button.
- The model receives the restored ID, columns and rows in a synthetic tool result after
  the current model-run boundary, and can use that ID in a Macro without rerunning SQL.
- Check explanation Asks after an earlier run consumed the original pending pair, and
  keep tool call IDs unique. Tests use stubs, with no live model or database.
