# 2. A number cited from an earlier Turn's Result appears without its SQL

**Status:** open · **Opened:** 2026-11-03 · **Source:** the SPEC §17 A17-M2 scenario runs (`explorer/SPEC.md` §17, raw runs under `docs/scenarios/austender/`)

Repo rules apply (`CLAUDE.md`, `explorer/SPEC.md`). New behaviour starts as a dated amendment with an ADR. Before the fix, write a regression test that fails for the reason described. Tests must never call a real model. Paths are relative to `explorer/agent/`, and code is named by symbol, not line number.

**Problem.** `Cite` placeholders in the prose can name any stored Result, including one from
an earlier Turn. When that Result isn't on the current Surface, the number shows with no
`SqlDetails` behind it. That breaks "every number on screen comes from the database, and the
SQL behind it is shown". The scenarios spec counts this as a real defect: "the explorer is
meant to show its working" (`explorer/specs/scenarios/SPEC.md`, review decision 1).

**Evidence.** In `runs-20261103T052659Z.jsonl`, `follow-up-first-supplier` run 3 asks "How many
contracts did the first one win?". The prose gives the right count (37), cited from Turn 1's
top-5 Result: the log has no typed-number warning for that Turn. The Surface shows only a
20-row contract list. The scorer reruns the Surface's SQL, doesn't find 37, and fails it
`missing`. Seen in 1 of 6 runs of this scenario on 2026-11-03.

**Options.**
- The server adds the `SqlDetails` of every Result the prose cites that isn't already on the
  Surface. This is deterministic, needs no model call, and the scorer then finds the number.
  The change is around `fill_prose` (`macros.py`) and `UiPipeline.build` (`ui.py`).
- A prompt rule: "a number in the prose must come from a Result shown on the Surface". It is
  cheaper to write, but the model may not follow it, and it adds prompt length.
