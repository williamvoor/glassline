# 3. A table that shows the same Result as a drilled chart stays Ask-only

**Status:** open · **Opened:** 2026-11-03 · **Source:** the SPEC §17 A17-M2 scenario runs (`explorer/SPEC.md` §17, raw runs under `docs/scenarios/austender/`)

Repo rules apply (`CLAUDE.md`, `explorer/SPEC.md`). New behaviour starts as a dated amendment with an ADR. Before the fix, write a regression test that fails for the reason described. Tests must never call a real model. Paths are relative to `explorer/agent/`, and code is named by symbol, not line number.

**Problem.** When a chart and a table come from the same Result and only the chart has a
`drill_sql`, a click on the chart is a Drill-down (about 0.02 s). A click on the same row in
the table is an Ask (about 6 s). The cap of two Drill queries per Surface
(`MAX_DRILLS_PER_SURFACE`) counts Visuals, so the model has to spend both on one Result to
cover both Visuals.

**Evidence.** In `runs-20261103T052659Z.jsonl`, `value-by-fy` run 3: the chart has a Drill
query, and the "Yearly totals" table from the same Result doesn't. That's 1 of 25 clickable
Visuals in the run. The model usually gives both Visuals a Drill query.

**Options.**
- A table reuses the Drill query of a chart built from the same Result, and the cap counts
  Drill queries instead of Visuals. This touches `_register_visual` (`macros.py`).
- Defer. At about 1 in 25 Visuals the gain is small.
