# 7. Model failures during an Ask are reported as successful Levels

**Status:** open · **Opened:** 2026-11-03 · **Source:** code review and re-review, reproduced with a failing stub model

**Priority:** P2

**Problem.** `LlmLoop.__call__` in `explorer/agent/src/explorer_agent/llm.py` returns
model-service failures and timeouts as prose-only `UiResult` objects.
`ExplorerExecutor._model_run` in `explorer/agent/src/explorer_agent/executor.py` then sends
them with successful `explorerLevel` metadata. The client treats a failed Ask as a new
Level, replacing the currently shown view with error prose and offering no Retry action.
The existing `UiError` handler does not cover these returned failure results.

**Evidence.** Answer a question with the stub fixture, then send a row Ask whose model
completion raises `ValueError`. The final prose is
`The model service failed (ValueError). Please try again.`, but the final metadata contains
`explorerLevel` for Level 2 rather than `explorerActionFailed: true`. The client handles
this as a successful response in `ExplorerApp.runAction`
(`explorer/client/src/app.ts`). The timeout fallback follows the same result path.

**Options.**

- Carry an explicit failure outcome from the tool loop to the executor, distinguishing
  failed model runs from legitimate prose-only answers.
- For a failed Ask, send the action-failure metadata used by other rejected or failed
  Actions, so the client keeps the existing Level and offers Retry.

**Acceptance criteria.**

- Add regression tests for a model-service error and a timeout during an Ask, using stubs.
- Failed Asks show an error and Retry in place, preserve the current view and Breadcrumb,
  and do not announce a successful new Level.
- A successful retry shows the resulting Level normally. Legitimate prose-only answers
  continue to work.
