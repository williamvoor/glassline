# 8. Interrupting a teacher baseline loses all newly completed answers

**Status:** open · **Opened:** 2026-11-03 · **Source:** re-review, reproduced with cancellation and stub completions

**Priority:** P2

**Problem.** `run_baseline` in `glimmer-tune/a2ui_eval/teacher.py` waits for every new
completion through `asyncio.gather` before writing the predictions file. Completed answers
remain only in memory until the slowest call finishes. Interrupting the run loses all newly
completed answers; resuming repeats those paid calls because only saved predictions are
recognised as done. An existing predictions file retains its older answers, but none from
the interrupted invocation are added.

**Evidence.** Run two fixture rows with one worker. Let the first stub completion return an
answer, block the second, then cancel `run_baseline`. No predictions file is created, even
though the first completion finished. This reproduces without a network or model call.
`run_baseline` describes itself as resumable, but currently saves progress only after an
entire invocation finishes.

**Options.**

- Persist each completed prediction through a serialised writer, preserving the existing
  resume behaviour that skips successful rows and retries errors.
- Atomically checkpoint the accumulated predictions as calls finish. The final write can
  still restore the requested row ordering.

**Acceptance criteria.**

- Add a regression test that cancels after one stub completion has finished while another
  is blocked, then resumes from the saved file.
- The completed answer survives cancellation and is not requested again on resume.
- Concurrent completions produce readable JSONL without lost or duplicate predictions;
  error rows remain eligible for retry.
- Tests never call a real model or incur cost.
